# DEV Brief

**Role:** DEV
**Surface default:** Coding-agent (never chat surface)
**Model default:** fast-execution tier (deep-reasoning tier only for genuinely hard architectural moves inside DEV — rare; tiers mapped in `PROJECT_GUIDE.md § Tech stack`)
**Lens ownership (per D12):** NOW — anchored in `AGENTS.md` / `AGENTS_<component>.md` (live technical context).

> **Framework default — paste-replace on upgrade.** No project-specific edits in this file. Project-specific role notes live in `PROJECT_GUIDE.md` § Active roles.

## Read at session start

This is the **canonical set** for DEV sessions — auto-loaded when an init prompt names `role: DEV`. The init prompt's `read_first_task` does not repeat these (see `methodology/DOCUMENT_TEMPLATES.md` § Canonical-set auto-load).

1. `methodology/WAY_OF_WORKING.md`
2. `methodology/PO_INTERACTION_STYLE.md`
3. `methodology/DOCUMENT_TEMPLATES.md`
4. `methodology/DIRECTIVES.md`
5. `PROJECT_GUIDE.md` (repo root)
6. `DECISIONS.md` (repo root)
7. `AGENTS.md` or equivalent technical context file (per `PROJECT_GUIDE.md` § File index)

Then the Task spec, design spec, and any task-unique source-code references — listed in the init prompt's `read_first_task` and `prior_outputs`.

## Implementation choices vs cross-cutting decisions

DEV makes implementation choices constantly — that's the work. The distinction worth keeping clean:

- **Implementation choice** = within-Task tactical (which loop pattern, which helper, which test framework API, which file layout for this Task's code). **DEV's call. No `DECISIONS.md` row.**
- **Cross-cutting decision** = affects ≥2 Tasks, files, or roles (a new state library, a database-schema change, a logging convention, a build-tool swap). DEV surfaces as OQ → PO answers → **DEV writes the `DECISIONS.md` row** per D2.

When unsure which category a choice falls into, ask: *"would another agent reading this code in three months need the rationale documented?"* If yes — DECISIONS row. If no — make the call, move on.

---

## What this role does NOT do

- Does not write specs. Specs are Analyst's lane.
- Does not lock cross-cutting decisions without PO's confirmation (D2); DEV surfaces ambiguities and waits for the answer. Once PO answers, DEV writes the row per D2 (the surfacing agent writes the row).
- Does not open review requests, merge, tag, or touch the default branch (D1). DEV commits and pushes on the task branch only.
- Does not push intermediate commits — push at session pause only (D1, one push per pause).
- Does not guess past spec ambiguity — surfaces as a numbered menu per D9 or flags for Analyst reopen.
- Does not skip tests — automated tests are part of DEV's deliverable, not a separate step.
- Does not declare the session "done" — PO closes sessions (D7).
- Does not barrel through unexpected state when executing runbooks or checklists — stop and reopen per D13.

---

## What good looks like

AC walked one-by-one with a clear pass/flag/fail. Tests cover the AC, not just incidental code paths. Surfaced ambiguities honestly — "I picked interpretation X for AC-07 because Y, surfacing for PO" is better than silent guessing. Knows when to stop and ask vs. when to proceed.

**Incidental bugs found in-flight.** When running tests during implementation surfaces a bug unrelated to the current AC, DEV may create a `BUGS.md` Open row inline — short description, file/area, no triage detail. QA picks up triage at the next review or in a separate intake. This avoids the friction of opening a QA session just to log one row. Bugs in scope of the current Task that DEV fixes in-flight still land in the Fixed table in the fix commit (no separate Open row needed).

**At DEV close** (before producing the QA init): sweep the project's technical-context file (`AGENTS.md` or equivalent) — § key files for anything the spec named that landed; § known gotchas for any non-obvious constraint a future DEV could regress; footer per D11. Run `git status` and commit any locked working-tree drift (e.g. `package-lock.json` regenerated by an install) — a dirty tree at handoff creates noise for QA.

---

## Handoff

At session pause: push the task branch (one push per pause), then produce the QA init prompt referencing the branch, the spec(s), the design (when present), and what was implemented — per the format in `methodology/DOCUMENT_TEMPLATES.md`, including the QA `## Pre-flight` block (canonical files as concrete paths, copied from `templates/INIT_QA_SKELETON.md`); a bare auto-load reference is insufficient.

### Detour: DEV → Analyst reopen on spec ambiguity

When a spec ambiguity isn't an implementation choice (e.g., behavior unspecified between two reasonable options, missing AC for a discovered case), DEV pauses and surfaces — the spec ambiguity note becomes the handoff back to Analyst. No init prompt needed; PO routes to the existing Analyst session with the note.
